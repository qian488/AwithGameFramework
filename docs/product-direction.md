# 产品形态与框架调整方向

确认日期：2026-11-01。状态：产品方向已确认，作为后续结构、功能与工具调整的依据；具体实施分阶段推进。当前实现与验证状态分别见[架构总览](architecture/overview.md)、[路线图](roadmap.md)和[最近验证](validation/latest.md)。本文中的目标形态不代表已实现能力。

## 产品定位与要解决的问题

AwithGameFrame 的目标是提供一套克隆后即可用于持续开发具体游戏的 C# 工程基座，容纳公共框架、游戏业务代码、引擎客户端工程、服务端工程和开发工具。开发者使用自己选择的 AI 编程工具，通过仓库提供的上下文、规范、skill、模板和命令完成开发。

优先服务维护者自己的长期游戏开发需求。近期面向独立游戏，以 2D 为重点，兼顾 3D、动作与战斗体验。玩法与体验参考《蔚蓝》和《传说之下》。长期保留适配 UE5 和承载更大规模游戏的演进方向。

需要解决的核心问题是重复编写通用代码，以及 AI 快速生成代码之后的持续维护困难。维护困难主要表现为模块互相牵连、同类功能采用不同实现并产生重复，以及对话变长或更换 Agent 后丢失已有设计。框架调整应优先减少这些问题。

## 已确认的使用方式

1. 开发者克隆完整仓库，在框架规定的区域创建具体游戏与选定的引擎工程。
2. 默认一个游戏使用一份独立仓库，以隔离代码、依赖、配置和构建；目录与工具保留同仓库多个游戏的组织能力。
3. 一个游戏通常选定一个主引擎，近期重点为 Unity 和 Godot .NET。多平台、多渠道发布使用该引擎的构建能力。
4. 公共框架和具体游戏中可独立于引擎的代码在引擎工程外开发、编译，再将所需产物接入游戏工程。游戏代码有框架明确提供的放置区域。
5. 跨引擎设计用于降低将来迁移的成本，通用业务与引擎实现之间保持清楚边界。近期交付围绕单个游戏实际选择的引擎展开。
6. 工程外的游戏代码与服务端均使用 C#／.NET；引擎适配遵循相应引擎的版本和运行环境要求。

## 代码与工程的职责

下表定义职责。已落地的游戏目录与构建接入方式见[工作区入门](getting-started/game-workspace.md)，后续能力仍按路线图逐项实现和验证。

| 区域 | 应放置的内容 |
| --- | --- |
| 公共框架 | 可复用运行时、技术基础设施与稳定契约，供具体游戏和宿主按需引用 |
| 游戏代码区 | 游戏自己的领域规则、应用编排、共享契约和专用模块；战斗计算、背包规则、任务规则等尽量在引擎工程外独立开发 |
| 引擎与平台适配 | 原生对象、资源、生命周期和设备的接线；暴露引擎类型的接口及必要实现 |
| 客户端工程 | 引擎要求的工程设置、场景、资源、表现、必要脚本与接线，以及接入后的框架和游戏产物 |
| 服务端工程 | .NET 服务启动与组合、技术基础设施接入、游戏所需的服务端代码及对应构建入口 |
| 配置与协议源 | 可编辑的源数据、契约及生成输入，在引擎工程外集中维护；生成结果按宿主需要接入 |
| 开发支持 | 构建、生成、接入命令，模块上下文、规范、skill、模板和维护说明 |

能合理放在引擎工程外维护的内容优先外置，同时保持引擎原生功能的正常使用。游戏工程保留必要内容；Spine、TextMeshPro（TMP）等项目组件由开发者在实际游戏工程中安装、配置和维护。

可独立计算的领域规则采用函数式设计：显式输入输出、输入不被修改、结果所有权清楚。应用层采用命令式编排，负责状态提交、流程和外部效果。引擎对象、资源租约与生命周期按自身所有权建模，规则细节沿用[函数式核心指南](guides/functional-core.md)。

框架公共代码保持独立于具体游戏的依赖方向。客户端与服务端按需共享契约和规则，进程状态、部署及原生能力分别归属于对应宿主。

## 基础能力与业务沉淀

当前阶段先完善业务逻辑之外的技术基座：工程组织、模块边界、构建与接入、运行时基础、网络与服务端基础、开发支持和模板。保留并整理已有能力，按实际接入流程补齐缺口。

战斗、背包、任务、活动、商店和商业化等业务，在实际游戏中实现。经过开发与维护，确认有复用价值的部分，再整理为框架模块、模板和使用说明；具体游戏始终有自己的实现区域。

单机、联网都属于目标场景。联网同时包括账号、云存档、活动等在线业务，以及同局合作或对战等实时联机场景。框架交付范围包含服务端基础与工程模板；各类业务流程、实时同步策略和生产部署方案按真实需求确定，不能由现有 HTTP/WebSocket 能力推定已经具备。

## AI 协作与可维护性

开发者继续选择自己的 AI 编程工具。框架交付上下文、规范、skill、模板和可执行命令，支持开发者按任务调整自己参与设计、实现与审查的深度。当前 AgentKit 的实际使用见[入口文档](../agent/README.md)。

框架调整应落实以下要求：

- 模块职责、公开契约、依赖方向与修改影响清楚，减少跨模块牵连。
- 同类功能有首选结构和可复用范例，Agent 能找到并复用已有能力。
- 模块入口、关键设计原因、兼容性与使用限制随仓库维护；任务按需收集上下文，支持新对话、更换工具与交接。
- 创建、构建、生成和接入流程具有明确命令、输入输出与失败说明，开发者能够理解结果并接手代码。

当前阶段的协作支持保持上述范围，复杂的模型接入、任务调度和自主 Agent 系统留在范围之外。测试专项与相应 skill 后续单独规划，现有检查的执行范围仍按具体任务记录。

## 第一阶段的调整顺序与完成条件

按以下顺序细化方案和实施，具体进度在[路线图](roadmap.md)维护：

1. 定义公共框架、游戏代码、客户端与服务端的目录职责和依赖，保留示例独立用途。
2. 明确工程外代码的构建产物、接入与更新方式，打通游戏创建、模块创建、独立编译、客户端接入和服务端启动流程。
3. 提供一致的模块/宿主模板、维护说明、上下文与命令，再沿实际开发流程补齐基础设施。

第一阶段完成时，开发者应能够克隆仓库，在指定区域创建选定引擎的客户端及按需使用的服务端，在工程外编写游戏代码，完成构建、接入、调试和对应发布。通用代码容易复用，多轮需求变更之后仍能理解边界、判断影响并继续维护。具体命令、平台和验收证据由实施任务补齐。

用 Test 的实际需求验证技术基座，按开发过程遇到的问题补强工具和通用契约。业务规则先在具体游戏内维护，有明确复用需求时再提取。

## 尚待确定的实施方案

2026-11-02 已确定第一批实施方案：具体游戏放在 `games/<Name>`，独立代码放在 `src`，客户端在 `client/Unity` 或 `client/Godot`，服务端在 `server`；引擎工程由开发者自行创建。框架及游戏外部代码构建为 DLL/PDB，Unity 通过生成的嵌入式 UPM 包接入，Godot 通过 DLL 与 MSBuild 导入文件接入；细节与限制见[工作区架构决定](architecture/decisions/0002-game-workspace-and-binary-integration.md)。这些决定落实工程基础，真实项目的调试、平台发布与后续能力仍需单独验证。

以下事项继续保留：

- 服务端技术组件、通信与实时同步方案、部署拓扑待需求细化；C#／.NET 已确定，具体依赖选型尚未确定。
- H5、UE5 和更大规模游戏属于后续方向，所需语言桥接、实现与平台验证单独评估。当前 C# 边界不等于已支持这些目标。

后续框架调整引用本文说明对应目标与交付范围。新增产品决定在本文更新，架构取舍记录在 [架构决策](architecture/overview.md)。
