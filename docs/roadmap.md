# 框架能力与后续方向

框架调整以[产品形态与方向](product-direction.md)为依据：克隆仓库开发具体游戏，业务代码尽量在引擎工程外，客户端与服务端均使用 C#；默认一游戏一仓库、一个主引擎。当前优先补齐技术基座和真实项目接入，再从实际开发沉淀业务模块。

当前实现的宿主为 Unity 与 Godot .NET。已有 Headless 与真实引擎样例及对应历史验证，下表描述实现范围，具体平台和源码状态以[验证基线](validation/latest.md)为准，不把可扩展边界当成所有引擎都已支持。

## 已有运行时基础

| 领域 | 当前能力 |
| --- | --- |
| 宿主与流程 | 实例 GameHost、独立服务/事件、显式异步模块依赖、启动回滚、取消、暂停恢复、主线程调度、FlowMachine 与导航 |
| 时间与对象池 | 缩放/未缩放游戏时间、一次/重复定时器、Delay、停止清理；普通 C# 对象池的预热、容量、借还所有权与租约 |
| 展示与交互 | 视图层级、模态、焦点、输入路由、显式属性绑定、Single/Additive 场景所有权和失败清理；Unity/Godot 后端 |
| 输入与音频 | 动作/上下文/重绑、按下/保持/释放、UI 优先消费、失焦释放；音量分组、并发/循环/暂停与资源回收 |
| 本地化与设置 | 实例语言/父语言/默认回退、文本绑定、统一语言/音量/按键恢复、设置保存竞态与关闭重试 |
| 数据与存档 | 持久化与真实编解码器契约、严格选项拒绝；版本化存档迁移链、原子封装、备份、checksum 与损坏恢复 |
| 配置与协议 | 可审查 schema、枚举/列表/嵌套结构、UTF-8 JSON/CSV、强类型生成、结构校验及兼容性基线 |
| 资源与内容 | 资源 scope/共享加载/取消清理、有限空闲 LRU/预加载；AssetBundle/PCK 构建、发布、HTTP 校验下载/续传与原子版本激活 |
| 可选网络 | HTTP 错误/超时/取消、正文大小限制与会话隔离；WebSocket 心跳/有限重连/显式连续推送恢复契约，localhost 真实连接测试 |
| 适配与演示 | Unity 与 Godot .NET 实例宿主、按需集成、两端和 Headless 共用的完整交互应用 |
| 可维护性 | 纯设置与布局规则、命令式应用服务、依赖边界检查、包元数据/GUID 检查、生成结果检查与结构化生命周期诊断 |

Godot 宿主实现每树退出协调和启动期暂停回放。存储实例捕获配置，视图和场景服务负责原生对象清理。

这些能力有明确边界：缓存预算仅统计空闲资产的后端估算；Godot PCK 属于进程挂载，不能卸载或替换同 namespace；内容链分发原始文件和已构建引擎资源；推送恢复要求产品实现服务端补查契约。具体接入见各包 README 与[资源流水线](guides/content-pipeline.md)。

## 开发期工具与模板

Unity 工作区提供[画面自动验收](reference/unity-visual-verification.md)。项目可定义控件布局断言、画面异常阈值和基准图，后台输出实际画面、差异图和报告。

Unity 编辑器自动化还提供持久化操作审计和 `performance.inspect` 快照，可记录编辑器操作结果、对象/组件数量和 Profiler 内存计数。它们用于发现明显异常，不能替代目标设备上的持续性能和人工画面验收。

已有 [AgentKit](../agent/README.md)：任务读写范围与脏工作区基线、模块发现与按模块选择的有限上下文/预算、固定工具目录、具体计划与真实确认、执行日志/耗时、机器检查与人工评审分离、本地事件监看。提供任务/评审/交接模板及可编译的[Domain/Application 功能模板](../templates/portable-feature/README.md)，标准验证包含工具契约、文档本地链接、行为回归和模板。

仓库级技能覆盖框架维护、具体游戏开发和 Unity 编辑器操作。开发工作流包含设计澄清、规格、可复现诊断、工单分诊、限范围原型、架构改进和评审。AgentKit 保存工单依赖、执行证据与交接记录，并对照本地议题快照。Unity 工作区附带本地诊断与编辑命令，支持同场景事务、项目白名单和场景与 Prefab 检查点。工作流覆盖和边界见[编辑器自动化](reference/unity-editor-automation.md)，实测结果见[最近验证](validation/latest.md)。

开发控制台在本机浏览器中运行工作区构建、客户端同步、配置与协议生成、测试和仓库验证，展示命令输出和退出状态。 [开发控制台](../tools/DevPanel/README.md)

## 当前优先：技术基座与游戏工作区

游戏工作区的首批实现见[入门步骤](getting-started/game-workspace.md)与[架构决定](architecture/decisions/0002-game-workspace-and-binary-integration.md)。本批提供代码骨架和命令；真实客户端由开发者创建后，继续确认导入、调试和目标平台发布，不能以工具实现替代原生验收。

- [x] 定义 `games/<Name>` 的领域/应用、客户端、服务端、配置/协议源职责；公共框架保持独立，默认一游戏一仓库，保留多个游戏的组织能力。
- [x] 提供工程外 C# 构建及 Unity/Godot DLL/PDB 接入与更新命令，明确生成目录归属；开发者自行创建客户端并安装 Spine/TMP 等组件。
- [x] 提供 .NET 服务端模板，包含配置、日志、宿主驱动和正常退出；共享契约/规则与宿主基础设施分别维护。
- [x] 提供 `new`、`paths`、`new-module`、`build`、`sync`、`run-server` 命令，脚手架不创建实际引擎工程。
- [x] 通过 `game.ps1 config` 接入游戏级配置生成和产物检查，Test 使用 JSON 与 CSV 验证招式引用和 Unity 接入。
- [x] 为游戏工作区提供协议源、兼容性基线和 `game.ps1 protocol` 生成/检查入口；共享协议示例继续保留独立入口。
- [x] 在开发者创建的 Test Unity 客户端验证工作区导入、脚本编译及已记录的构建目标。 [验证记录](validation/latest.md)
- [ ] 在具体项目中验证调试和所选平台的实际发布流程，按项目需求选型服务端组件。

第一阶段的交付条件见[产品方向](product-direction.md)：能够建立游戏、在工程外开发、接入选定引擎、按需启动服务端，并完成对应调试与发布。每项完成状态须以实际产物和检查范围记录。

## 从真实游戏沉淀业务模块

以 Test 的实际需求检验现有能力。先沿对应的领域规则、应用编排、Unity 接入或服务端入口实现并验收。遇到跨层问题时，核对现有公共契约和参考项目的职责分工，再判断是修正框架能力、更新接入工具，还是继续由 Test 负责。框架改动以触发它的 Test 路径作为回归依据。 [Test 工作区](../games/Test/README.md) · [架构参考](architecture/decisions/0001-engine-independent-runtime.md#本地参考项目)

战斗、任务、背包、数值、活动、商店、商业化、登录/登出和具体推送补查等先在游戏区域实现。经过实际迭代后，再提取有复用价值的模块、契约与模板；当前阶段的基础交付围绕技术基座推进。

## 长期方向与待定事项

后续可在 Web 工具中增加独立的 AI 原型页面。先围绕一个具体 UI 原型定义可编辑、可版本化的资产，再通过 Unity uGUI 导出验证布局、资源绑定与重复生成。其他 UI 系统按各自需要实现导出。

H5、UE5 和更大规模游戏保留后续演进方向，需要独立的适配、构建与运行验证。框架升级与游戏独立演进的机制尚未确定，后续按维护者真实项目的同步需求决定。

新增工作先明确产品、服务端或目标平台约束和验收范围，再决定是否进入通用框架。涉及平台能力时记录真实构建与运行结果。其他语言优先复用数据、协议和兼容性规则，再选择独立桥接或实现。
