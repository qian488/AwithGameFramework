# AI 协作与代码评审

本指南把开发者偏好转化为可执行的协作检查。它服务于框架、具体游戏和 AgentKit 任务，帮助开发者判断什么时候立即修改，什么时候记录后续工作。

## 三层约束

仓库硬约束用于保护依赖方向、资源所有权、生命周期和可验证性。它们必须遵守。

默认建议用于减少重复决策。项目可以根据规模、阶段、性能和平台目标调整，但调整理由应写在任务说明或模块 README 中。

个人偏好用于改善协作体验。它们可以写入项目根 `AGENTS.md` 或任务说明，不自动升级为所有项目的公共 API 约束。

## 先诊断再修改

遇到故障时，先记录以下事实：

- 触发步骤、输入、运行模式、引擎版本和平台。
- 预期结果、实际结果和首次出现异常的边界。
- 最短可复现命令、测试或场景操作。
- 能区分候选原因的日志、断点或最小探针。

修改后重复同一条检查，并保留最小回归检查。正常控制流中的早返回可以保持安静。配置错误、资产过期、生命周期错误、恢复路径和不可预期失败需要带有模块、操作和上下文的日志。

## 复利债务判断

代码问题是否立即修复，优先看它是否会在后续工作中反复出现：

1. 当前逻辑是否已有多个调用者。
2. 后续需求是否大概率会修改同一段代码。
3. 问题是否会让每次诊断、验证或资源维护都增加成本。
4. 当前修复是否会扩大多个模块的改动面。
5. 暂缓时是否已经记录具体触发条件、影响范围和负责位置。

会重复产生维护成本的问题应在当前切片处理。只影响一次性演示、暂时没有复用入口且改动面较大的问题，可以记录为后续任务。

文件行数本身不决定是否拆分。只有当职责具有独立输入、独立生命周期、独立验证方式或出现第二个调用者时，拆分才会降低维护成本。

## 代码可理解性

合入前，开发者或评审者应能回答以下问题：

- 从哪个入口进入，状态和数据经过哪些边界。
- 每个新增抽象解决了哪个真实调用者的问题。
- 错误、取消、重试和资源释放如何处理。
- 哪些分支是正常控制流，哪些分支代表异常或恢复。
- 生成内容、运行时实例和持久化数据分别由谁拥有。

AI 生成的代码需要经过开发者理解和解释。机器检查通过代表当前检查条件满足，人工评审仍需确认设计、边界和可维护性。

## 通信与复用

跨所有权的状态通知、生命周期通知和 UI 刷新通知可以使用 `EventBus`。命令、查询和组合根内的协作保留显式接口或直接调用，让调用关系可以沿入口追踪。

小而确定的对象池可以使用框架的 `ObjectPool<T>` 或项目自己的实现。并发、诊断、跨平台和复杂生命周期要求出现时，再评估成熟库。是否采用库由实际约束决定。

规则、配置和内容生成采用数据驱动的范围由变化频率和维护者决定。算法规则仍应保持显式输入和输出，编辑器参数可以由资源、JSON 或表格提供。

## Test 示例

`Test` 提供了几种可复用的示例：

- `Test.Domain` 保存公式、战斗时序和其他确定性规则。
- `Test.Application` 采集事实、推进状态并提交表现效果。
- Unity 客户端保存资源、Inspector 工具、预览和真实引擎接线。
- Rain Pass 使用参数资源、确定性生成器、运行时模式、预生成 Prefab、来源标记、输入哈希和 manifest 校验。
- 纯规则使用 .NET 测试，Unity 行为使用真实编辑器测试，画面、声音和手感保留人工验收。

这些内容用于说明职责和验证方式。具体游戏生成器、资产路径和表现规则继续归具体游戏所有。
