# 编写和维护文档

先确定读者要完成什么，再决定文档的位置和内容。新接入者、框架维护者和自动执行任务的 Agent 需要不同深度的信息，不要求他们读完开发过程才能找到入口。

## 按读者任务放置

| 读者的问题 | 放置位置 | 内容 |
| --- | --- | --- |
| 这是什么，从哪里开始 | 根 README、区域/包 README | 用途、最短可运行入口、局部导航 |
| 怎样完成某件事 | `docs/guides` | 前提、输入、步骤、结果和验证 |
| 接口、参数、命令有什么限制 | 包 README、`docs/reference` | 当前行为、选项、错误、线程与所有权契约 |
| 为什么采用这个边界 | `docs/architecture` 与决策记录 | 背景、决定、后果与替代状态 |
| 旧代码怎样升级 | `docs/migrations` | 旧入口到新入口、破坏性变化、迁移步骤 |
| 哪些版本和平台真的运行过 | `docs/validation` | 实际环境、命令、结果、证据与未执行项 |

这种分类借鉴 [Diátaxis](https://diataxis.fr/) 对学习、操作、参考和解释的区分。文档索引负责把任务引到唯一入口，不在每个入口复制完整使用说明。

## 描述当前事实

使用说明对照当前源码、脚本和输出编写。写“现在怎样使用”，把“曾经怎样、下一步准备怎样”分别放入迁移、决策、任务或历史记录。建设过程中的讨论、失败尝试和反复确认不进入长期操作步骤；影响当前选择的限制应保留。

架构决策按独立记录保存，列明背景、决定、后果和状态。新决定替代旧决定时保留旧记录并标记替代关系，不把旧决定改写成一直如此。做法参考 [Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)。历史资料仅供追溯，不作为当前开发约定。

把聊天或工作记录整理成文档时，重新构建未参与讨论者需要的上下文。永久有效的修正写入相应步骤；一次性的本机命令输出、工具执行过程和构建叙述保存在验证记录或本地报告，不要求读者复盘对话。

## 精简时保留语义

一句话优先讲一个动作或条件，明确谁执行、对什么执行、何时执行以及失败后会怎样。使用主动语态，术语与代码标识符一致；第一次出现的必要术语用短句说明。

压缩文字时保留执行者、动作、对象、条件、义务程度和不确定性。例如“销毁节点前等待 `ShutdownAsync`”不能缩成“退出时清理”：后者丢失了时序和等待义务。“已验证 Windows 导出”也不能改成“支持全平台”。同一文档统一使用“必须”“建议”“可以”的含义，不把建议改成要求。

示例只保留完成任务所需代码，同时写清示例外部提供的对象、路径和配置。代码符号用反引号；步骤用有序列表，平行选项用表格或无序列表。链接文字说明目的，不用“这里”代替目标。

## 状态与证据对应

| 写法 | 需要的依据 |
| --- | --- |
| 已实现 | 当前源码和可说明的行为；仍需另列验证状态 |
| 已构建或测试通过 | 实际执行的命令、范围和结果 |
| 已验证某个平台 | 具体引擎版本、构建目标和原生运行结果 |
| 已人工验收 | 真实评审决定，不能用机器检查结果替代 |
| 计划、建议或推测 | 明确标注，不写成现有能力 |

证据应能定位到对应版本或工作区。记录尚未执行的检查和它们限制的结论；不因文档润色删除真实限制，也不为凑模板虚构前提。验证命令见 [参考](../reference/verification.md)，当前验收范围见 [最近记录](../validation/latest.md)。

## 修改后的检查

1. 从目标读者尚未读过聊天记录的状态重读，只靠文档及链接能否完成任务。
2. 检查本地链接、文件名、标题锚点、大小写和移动后的相对路径；更新唯一入口及实际引用，历史记录保持其时间语境。
3. 确认命令的工作目录、必填参数、版本前提、输出位置和成功条件。文档改动执行对应静态检查；行为或示例改变时运行适用验证。
4. 对照源码复核取消、异常、线程、所有权和兼容性条件，避免删段时丢失接口契约。
5. 保持协作规则唯一：`AGENTS.md` 给规则，`GUIDE.md` 给导航，编辑器规则只指向它们，不复制多套约定。
