# Test 双玩法擂台赛

两名玩家在 `CombatShowcase` 的 `Online PvP` 进入擂台赛，用同一个房间码加入本机 Test.Server。双方打完一局 Rain Pass 决斗和一局 BBads 背包对战，再看总比分和各局战报。局间界面显示刚结束的一局、当前比分、下一玩法和双方就绪状态。两人各自就绪后进入下一局，沿用原席位。

## 赛程规则草案

- 第一局是 Rain Pass，第二局是 BBads。每局胜者得一分，平局双方各得零分。两局后比分领先者赢得擂台赛。比分相同则进行一局 Rain Pass 决胜局，决胜局仍平则整场记为平局。
- 运行中的对局沿用各自的同步方式与现有 12 秒掉线窗口。恢复时 Rain Pass 补输入帧，BBads 取最新完整快照。主动退出擂台赛或在线对手等待对方超时则结束赛程，在线方以弃权获胜，比分保留已确认各局的记录。局间断线从服务端发现断开时起计时。两人均离线且均超时则赛程记为中止。
- 服务重启后，原席位凭据可以恢复擂台赛。已确认的比分、局序及战报直接读取。重启时尚未确认结果的对局，用同一规则和配置开一个新对局，双方就绪后重赛。恢复的局间界面也重新等待双方就绪。终局赛程直接打开战报。
- 战报展示每局胜者、结算原因和总比分。Rain Pass 保留初始种子、配置指纹和权威输入，供离线复算和定位哈希分歧。BBads 战报可查看双方终局背包和对战结果。弃权和中止在战报中显示明确原因。

## 选题依据

现有真实双客户端验证已经分别跑通 Rain Pass 的输入帧与哈希检查，以及 BBads 的服务端推进与快照恢复。服务端集成测试也明确验证了进程重启后原对局凭据失效。现在把两种玩法串在同一赛程里，可以测试同一玩家身份跨对局、旧消息隔离、结果落盘与状态恢复。 [PvP 实测](../../../../docs/validation/latest.md) · [重启测试](../../server/Test.Server.Tests/PvpServerIntegrationTests.cs)

Test 的委托成绩已经用 `VersionedSaveService` 持久化，委托回放已有内容指纹。擂台赛需要进一步验证，在一个结果同时影响比分、下一阶段和战报时，服务端能否让三者一起恢复。优先复用现有存储、协议生成和实时客户端入口。实现中如果出现存储提交、消息分发或后台验证的具体缺口，用可复现的用例判断是否由公共框架补齐。 [成绩服务](../../server/Test.Server/Runtime/ContractScoresModule.cs) · [委托回放](../../src/Test.Application/Runtime/Combat/ContractReplayStore.cs) · [已有 PvP 框架反馈](../pvp-framework-validation/framework-feedback.md)

## 职责与任务依赖

| 工单 | 所属层和交付 | 依赖 |
| --- | --- | --- |
| 1. 赛程规则与契约 | `Test.Domain` 实现计分、局序、平局与弃权规则。`Test.Application` 定义阶段、就绪流程和可恢复的赛程状态。协议从 `games/Test/protocol` 生成，区分擂台赛 ID、对局 ID 和赛程版本。 | 首先锁定状态与消息契约 |
| 2. 权威赛程与持久化 | `Test.Server` 接入现有两种对局，将对局结果、比分和赛程状态作为一次提交。先落盘再确认。以对局 ID 去重，旧对局结果与旧赛程版本不能推进当前阶段。服务端负责席位凭据和重启恢复。 | 工单 1 |
| 3. 战报与复算 | `Test.Application` 定义两种战报数据和查询入口。Rain Pass 用实际输入逐帧复算并校验，BBads 保存终局快照中的背包与结果。服务器将战报关联到已提交的对局。 | 工单 1，按契约对接工单 2 |
| 4. Unity 玩家流程 | Unity 接入建房、局间比分和就绪、断线提示、恢复和战报视图，按权威阶段切换到对应玩法。 | 工单 1 后可并行做视图，联调依赖工单 2、3 |
| 5. 后台全链路验证 | 扩展现有双 Player 验证入口，采集赛程阶段、两端比分、对局标识和战报结果。汇总真实引擎证据与框架反馈。 | 工单 2 至 4 |

## 验收

| 操作 | 可观察结果 | 验证方式 |
| --- | --- | --- |
| 同一玩家两局全胜，或双方各胜一局 | 前者以 2 比 0 结束，后者进入 Rain Pass 决胜。两端显示相同席位、比分和赛程阶段。 | Domain 规则、两个后台 Windows Player |
| 第一局平，第二局某方获胜。另跑两局平后决胜仍平 | 前者以 1 比 0 结束，后者整场为平局。 | Domain 规则、服务端集成 |
| 先在 Rain Pass 局内断线，再在转入 BBads 前断线 | 局内以原席位补帧。局间回到正确比分和下一玩法，双方就绪后各自进入同一局。 | 真实 WebSocket 集成、两个后台 Windows Player |
| 局间主动退出、单方超时、双方均超时 | 分别在战报中记录弃权原因或中止，保留此前确认的局分。 | Application 与服务端集成 |
| 结果已落盘时断开确认，重新连接后重发。另重放上一局的迟到消息 | 结果只计一次，双方能拿到同一战报，迟到消息无法推进当前阶段。 | 服务端集成故障注入 |
| BBads 局内重连，随后在结果提交前重启服务端 | 重连应用最新快照。重启后保留已确认的 Rain Pass 结果，BBads 获得新的对局 ID 并等待双方重赛。重启已结束赛程时直接读到战报。 | 服务端集成、两个后台 Windows Player |
| 查询整场战报并复算 Rain Pass | 两端战报与服务端结果相符。Rain Pass 的逐帧哈希匹配，BBads 终局背包与服务端快照相符。 | 自动化对照 |

真实 Unity 验证沿用后台批处理和隐藏 Windows Player。保留验证摘要并清理临时项目与运行产物。人工试玩从 `CombatShowcase` → `Online PvP` → 擂台赛进入，检查局间比分、就绪进度和掉线提示能否一眼看懂，以及从 Rain Pass 切到 BBads 时界面与输入提示是否清楚。 [现有后台验证入口](../pvp-framework-validation/integration.md)
