# Test 擂台赛大厅的 Web 原型与 Unity 交付

在 DevPanel 选择 Test，打开擂台赛大厅原型。开发者可以在浏览器修改控件布局、间距、文本、颜色和素材引用，在等待入场、局间就绪、重连和赛后战报之间切换预览。设计保存为游戏项目内可版本化的文件。经预检导入 Unity 后，同一套大厅界面出现在 `CombatShowcase → Online PvP → Tournament` 的真实双人流程中。

## 选题依据

擂台赛已经通过两个 Windows Player 的赛程验证。现有大厅和战报由 `PvpClientShowcase` 通过 IMGUI 绘制，连续运行验证覆盖了比分、恢复和战报数据，布局与可读性留给了人工。选用这个页面可以让原型针对实际状态及交互，并把长玩家名、掉线提示和战报滚动纳入自动验收。 [擂台赛界面](../../client/Unity/Assets/Scripts/Combat/PvpClientShowcase.Tournament.cs) · [现有验收记录](../../../../docs/validation/latest.md)

DevPanel 已能按游戏选择构建、同步和检查，路线图也已列出可编辑、可版本化的 Web 原型。Test 的委托面板已经具备 uGUI Prefab 和后台 Overlay 截图流程。这个试点要验证从 Web 编辑到原生资源交付的一段缺口，包括更新设计时能否保住场景引用，以及浏览器预览通过后能否在真实 Unity 布局中复验。 [DevPanel](../../../../tools/DevPanel/README.md) · [路线图](../../../../docs/roadmap.md#长期方向与待定事项) · [Rain Pass 界面验证](../../README.md#雨夜委托)

## 页面和交互草案

| 阶段 | 玩家看到和可以操作的内容 |
| --- | --- |
| 入场 | 服务地址、房间码和玩家名，以及加入按钮。连接失败时在表单旁显示原因，可保留输入重试。 |
| 等待和局间 | 当前比分、下一局玩法、双方连接及就绪状态。两人连接后可以确认就绪。点下后显示自己的就绪状态，等待对手。 |
| 重连与服务器重赛 | 显示已确认比分与当前恢复状态。连回原局时继续当前玩法。服务端恢复到局间时显示要重赛的玩法，并等待双方重新就绪。 |
| 结算 | 显示胜负或中止原因、总比分和按局排序的战报。BBads 一局可展开两个终局背包。返回后重新进入同一房间可查看已保存的战报。 |

草案采用现有的英文界面用语，首轮验证分辨率选为 **1280×720、1920×1080 和 3440×1440**。常用控件支持鼠标、键盘和手柄，比分与就绪状态同时通过文字表达。开发端用固定赛程数据快速预览所有状态，运行端从同一条擂台赛会话接收权威状态。

## 从原型到资源

1. **编辑。** DevPanel 增加游戏范围内的原型入口。浏览器和 AI 使用同一份 JSON 源，记录稳定节点 ID、受支持控件、布局、视觉属性及绑定键。首批控件覆盖容器、文本、图片、输入框、按钮、滚动区，以及比分和背包格需要的列表模板。设计使用项目已有的字体和项目资源键。
2. **预检。** 展示节点和资源的差异，列出缺少的素材、重复 ID、失效绑定及受影响的 Prefab。预检阶段只生成报告。应用前先在隔离项目生成并校验完整 Prefab，成功后更新正式资产。错误报告定位到文件与节点 ID。
3. **导入。** Unity 编辑器将设计编译为可在 Inspector 查看和调整的 uGUI Prefab。输出固定在 Test 的 Unity 资源目录，保留既有 Prefab 的 `.meta` 和 GUID。生成内容按稳定节点 ID 更新。开发者的表现接线和手工扩展放在独立外层 Prefab，生成更新以其内部的生成视图为单位。
4. **运行。** Unity 将绑定键接到现有的加入、就绪、退出和战报查看入口。赛程推送继续通过既有 Application 会话，Unity 将数据显示为页面视图。先用等待室完成从原型到真实连接的纵向切片，再扩到局间、恢复和结算。

## 职责和工单

| 工单 | 写入范围与交付 | 依赖 |
| --- | --- | --- |
| 1. 页面契约 | Test 设计目录和游戏 UI 原型源，定义状态、可编辑属性、绑定键、素材引用及验收样本。 | 先确认页面状态与控件范围 |
| 2. Web 编辑器 | `tools/DevPanel`，提供选择游戏、读取、编辑、状态预览、保存和发起预检的通用操作。具体页面从游戏项目读取。 | 工单 1 |
| 3. Unity 导入 | Unity 侧编辑器工具和 Test 的生成资源。实现预检、稳定节点匹配、更新报告和原生 Prefab 导入。通用控件映射留在 Unity 工具侧，Test 持有资源目录和具体页面绑定。 | 工单 1，可与工单 2 并行 |
| 4. 玩家流程接入 | Test 的 Unity 表现和必要的 Application 投影，把真实会话和 UI 接好，覆盖就绪、重连、重赛及战报。 | 工单 1 后可开发绑定，联调依赖工单 3 |
| 5. 双端与画面验收 | Test 验证清单、固定数据和后台脚本，复用现有双 Player 冒烟与画面工具，记录实际流程和负例。 | 工单 2 至 4 |

Domain 负责擂台赛规则，Application 负责会话及可消费的数据，Test.Server 负责权威阶段和持久化。DevPanel 和 Unity 导入器共同消费设计文件，原生控件类型和生成过程归 Unity 工具，Test 页面与素材由 Test 维护。 [工作区职责](../../../../docs/architecture/decisions/0002-game-workspace-and-binary-integration.md)

## 验收

| 操作 | 可观察结果 | 验证入口 |
| --- | --- | --- |
| 浏览器修改间距、按钮文字和背包图标，再刷新和重启 DevPanel | 重新打开仍读到同一份设计。Git 差异能定位到对应控件属性。 | 无头 Chromium 与设计文件对照 |
| AI 或开发者编辑同一份设计，再预览并导入两次 | Web 和 Unity 均反映改动。二次导入结果稳定，生成的控件层级、Prefab GUID、外层绑定和手工扩展保持有效。 | Unity 后台导入与差异检查 |
| 输入缺失的资源、重复节点 ID 或无法解析的就绪绑定 | 报告给出节点与原因，现有 Prefab 保持可用。修正后可重新导入。 | 导入负例，检查导入前后的资产哈希 |
| 用三种分辨率查看满员等待、对手断线和三局战报 | 比分、就绪按钮和恢复提示可见且互不遮挡。长名字和三局战报有可预期的裁切或滚动行为。故意压缩面板宽度时验收失败。 | Unity 后台截图、布局断言及基准对照 |
| 两个客户端从正式入口完成一次赛程，BBads 局中重启服务端 | 玩家操作真实 uGUI 控件，双方看到相同比分及重赛提示，重赛后看到一致的战报。 | 后台 Windows Player 与 Test.Server |
| 用键盘或手柄从房间表单走到战报 | 可到达所有主操作，状态切换后焦点落在当前可用控件。 | Unity PlayMode 输入注入，实体手柄体验 |

画面验证优先沿用隔离工程与无头浏览器，报告记录截图分辨率、状态与失败控件，运行后清理临时工程和 Player。人工验收观察界面切换观感、信息层级和实体手柄使用感。 [画面自动验收](../../../../docs/reference/unity-visual-verification.md)
